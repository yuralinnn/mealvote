# 🍽️ 朋友約飯神器

三五好友想聚餐但懶得找餐廳。發起人開一個房間、把連結丟群組，大家各自在自己手機上填三個問題，系統就依照全員的位置、可接受距離與想吃的類型配出餐廳，並開投票。

投票不是單純的舉手：每個人會抽到一個**只有自己看得到的角色**（國王、壞皇后、魔法師、笨蛋、平民），還會收到一間**全房共用的神秘店家**——投票時只知道類型、而且只有 10 秒可以決定要不要賭，結算後才公開是哪一家。票數在所有人投完之前對誰都不顯示。

## 它怎麼決定要推薦哪幾家

每個人填三件事：**所在捷運站**、**最遠可接受幾站**、**今天想吃什麼**（可複選）。

**第一道關卡是硬的：所有人的站數都要符合，不符合的餐廳完全不會出現。** 沒有「放寬讓某個人多坐幾站」這種事——與其推薦一家有人到不了的店，不如老實說配不出來，並指出是誰的條件卡住了。

過了這關之後，推薦分兩區：

**🔥 最多人想吃的** — 兩個人以上都選了同一個類型時，那個類型就是共識，各出兩家，並依照「幾個人選」由多到少排。三個人裡有兩個都想吃火鍋，火鍋就排第一。

**🎯 每個人各自想吃的** — 只有一個人選的類型放這裡，依成員順序分群。給幾家是**看「有幾種單人類型」，不是看有幾個人**：三種以內每種給兩家當備案，四種以上每種只給一家。

之所以用類型數而不是人數，是因為真正會讓畫面爆掉的是類型——三個人也可能各選三種不同的，變成九種類型。用類型數控制，卡片總數就穩定在 6 張上下。

這個決定由後端算好後直接帶給前端寫文案，不讓前端自己推，免得再出現「說兩家卻只給一家」的矛盾。

每張卡片右上角標的是**幾個人想吃這個類型**，這也是決定排序的關鍵，而且會依人數上不同顏色：全員都想吃是橘底白字最搶眼，接著綠、藍，只有一個人想吃是灰色。卡片下方列出**每個人各自要走幾站**——既然距離已經是硬條件，這裡的數字純粹讓大家看看誰比較辛苦，好喬。

同一類型內排序時，**個人小店優先於連鎖店**（不然畫面上永遠是那幾個連鎖品牌），**精選清單優先於 OSM 匯入**（精選的有價位、特色說明與訂位提示）。

如果大家想吃的類型完全沒有交集，「最多人想吃」那一區會是空的，畫面上會直接說明，讓大家從各自的選項裡挑。

### 距離是怎麼算的

內建雙北軌道路網 **139 站**：台北捷運六條主線（文湖、淡水信義、松山新店、中和新蘆、板南、環狀線，含新北投與小碧潭支線），加上新北捷運的兩條輕軌（淡海輕軌綠山線／藍海線、安坑輕軌）。輕軌透過紅樹林與十四張兩站與捷運轉乘，所以「幾站」算得過去。

兩站之間跑最短路徑，**先讓站數最少，站數一樣時再挑換乘次數最少的走法**。

之所以用「站數優先」而不是把換乘算進成本，是為了跟使用者填的「最遠可接受幾站」保持一致 —— 篩選跟顯示用的是同一個數字，不會出現「明明有 4 站的走法卻顯示 5 站」這種矛盾。

`新埔民生`（環狀線）與 `新埔`（板南線）站名不同但可以走過去，額外加了一條成本 1 站的步行連結。另外支援口語別名，打「北車」「101」「小巨蛋」「SOGO」「漁人碼頭」都認得。

填站名時是**自由輸入**，沒有下拉選單——139 站塞進 datalist 反而難挑。打到一半會跳出可以直接點的建議（打「忠孝」就給忠孝復興／忠孝敦化／忠孝新生），另外也可以按「🚇 依路線選擇」——路線依官方順序排列（文湖 → 淡水信義 → 松山新店 → 中和新蘆 → 板南 → 環狀 → 輕軌），點進去看到的是**該線由起點到終點的完整站序**，不是一坨排序過的站名。

## 投票怎麼跑

投票是**兩段式的：先勾、再送出**。這不是為了多按一下，而是因為壞皇后要毒「下一個投票的人」——複選模式下如果勾一下就算一票，根本沒有「這個人投完了」這個時間點可以定義先後。有了送出這個動作，順序就是「按下送出的先後」，大家各自在不同時間投也成立。

**送出之後不能反悔。** 票數在所有人投完之前對任何人都不顯示（包含發起人），畫面上只看得到「幾 / 幾 人已送出」。全員送出就自動揭曉；有人遲遲不投，任何人都可以按「不等了，直接結算」。

結算畫面列**前三名**（同票並列同名次，最多 5 列）、每一家是誰投的、這一局發生了哪些技能，以及全員的角色揭曉。想再來一輪就按「🔄 再玩一局」——票數歸零、**角色與神秘店家都重抽**，但大家填的條件會留著，不用重填。

## 互動機制 1：角色抽籤

產生推薦的當下，系統會發角色。**角色只有自己看得到**，畫面上不會顯示別人是什麼，避免影響投票心理。

| 角色 | 技能 |
| --- | --- |
| 👑 國王 | 投票權重 ×2，勾的每一家都拿 2 票 |
| 🍎 壞皇后 | 緊接在她之後送出投票的人被毒啞，那一票整張作廢。她是最後一個送出的話技能失效，而且她不會知道毒到誰 |
| 🧙 魔法師 | 送出時指定兩家餐廳，**所有人投完之後**它們的票數互換。指定當下看不到任何票數，是盲選。**就算被毒也照樣交換**——毒的是票，不是技能 |
| 🤡 笨蛋 | 不能自己選，按轉盤由系統隨機決定投給哪一家，只會投到一家 |
| 🧑‍🌾 平民 | 權重 ×1，不受任何技能影響 |

**五人以上**：四個特殊角色各出現一次，其餘都是平民。**五人以下**：從四個特殊角色裡隨機抽，抽到幾個算幾個——所以三人場每次的角色組合都不一樣。

技能的結算順序是固定的：先剔除被毒的人（那一張票整張作廢），再乘上國王的權重，**最後才做魔法師的交換**。這個順序讓「盲選」名副其實。

毒與魔法的關係要分清楚：壞皇后毒掉的是**票**，不是**技能**。魔法師被毒的話，他自己投的那幾家不算數，但他指定的兩家照樣會在最後對調。所以毒到魔法師其實只擋掉一票，攔不住他真正的殺傷力——揭曉畫面上會直接寫出來。

伺服器端才知道誰是什麼角色。對外的房間資料永遠不含 `roles`，成員只能拿自己的 `secret` 查自己那一份。

## 互動機制 2：今日主廚隱藏彩蛋

每個人第一次進到投票畫面時，關掉角色卡之後會立刻跳出「今日隱藏推薦」：**同一個房間裡所有人看到的是同一間**（房間建立推薦時決定一次，不是各自隨機）。

彈窗上顯示的是代稱（神秘店家 X／Y／Z／α／Ω）配一句宣傳詞，**不揭露店名**，但會明講兩件事：**它是什麼類型**，以及**大家都到得了**——它是從通過距離硬條件、但沒被選進推薦名單的店裡抽的，所以是額外的選項，不會擠掉正常推薦。有了類型這條線索，賭它才有依據，不是純粹擲骰子。

**投票選項就在彈窗裡，而且只有 10 秒。** 「🎲 賭一把，投給它」與「算了，不冒險」兩個按鈕，配一條會走完的倒數條。時間到自動關閉，**之後就不能再投給它了**——下面清單裡那張卡片會變成「⏳ 已錯過，不能再投」，按了賭一把的人則顯示「🎲 已押注」。這是刻意的：這個機制的重點是當下要不要賭，給人慢慢考慮就沒意思了。

決定會記在瀏覽器裡，所以**重新整理頁面不能重來一次 10 秒**。笨蛋沒有決定權（他投給誰由轉盤決定，而且轉盤不含這一家），彈窗上會直接說明。

**結算之後真面目就公開了。** 揭曉畫面會有一塊「神秘店家的真面目」告訴大家「神秘店家 Ω 其實是 ○○○」，排行榜與完整名單裡那張卡片也會換成真實店家，附上車站、價位與地圖／菜單／訂位連結——畢竟要真的去吃，總得知道是哪一家。

真實店家的資料**只在 `stage` 進到 `revealed` 之後才會出現在 API 回應裡**。投票期間拿 `curl` 直接打 `GET /api/rooms/:id` 也看不到，不是前端藏起來而已。

## 資料與隱私

- **沒有登入機制**，房間連結本身就是存取權限。
- **只收暱稱**，不收電話、Email 或任何聯絡方式。
- 角色、投票內容、彩蛋的真實店家都只存在伺服器端；`GET /api/rooms/:id` 這種公開端點不會帶出 `roles`、`ballots` 或成員的 `secret`。彩蛋的真實店家在投票期間同樣不外流，**結算後才公開**（這是刻意的，大家要知道去哪吃）。
- 資料**單場聚餐結束就可以丟掉**——程式會自動清掉 30 天前的房間，沒有長期保存的設計。檔案模式直接刪 `storage/` 目錄，資料庫模式 `DROP TABLE mealvote_rooms` 或整個換一個免費資料庫就好。

需要 Node.js 18 以上。

```bash
npm install
npm start
# → http://localhost:3000
```

## 部署

這是一個一般的 Node.js 伺服器，`npm start` 就會起來，`PORT` 從環境變數讀。

### 先講一件會影響選擇的事

房間資料要存在**重啟後還在**的地方。免費方案的主機幾乎都是「檔案系統暫時的」——服務休眠或重新部署之後，檔案會回到剛部署的樣子。

這對一般的小專案不痛不癢，但對這個 app 很致命：它的使用情境正好是「早上開房間、大家陸陸續續填、傍晚才投票」，中間一定會閒置。Render 免費方案**閒置 15 分鐘就休眠**，醒來時檔案已經清空——大家填的東西全沒了。

所以儲存層做成兩種後端，開機時自己判斷：

| 有沒有 `DATABASE_URL` | 用什麼 | 重啟後 |
|---|---|---|
| 有 | PostgreSQL | 資料還在 ✅ |
| 沒有 | `./storage/rooms.json` | 看主機的檔案系統 |

程式碼不用改，**部署時多設一個 `DATABASE_URL` 就切換過去了**。連不上資料庫也不會讓服務起不來，會退回檔案模式並在 log 印出警告。開機那一行 log 會直接寫現在是哪一種，`/healthz` 也看得到。

### Render（一步一步）

**0. 先把程式碼放到 GitHub**

專案裡已經有一個 git commit 了，只要建遠端 repo 再推上去：

```bash
cd mealvote
git remote add origin https://github.com/你的帳號/mealvote.git
git branch -M main
git push -u origin main
```

（還沒有 repo 的話，先到 github.com/new 建一個空的，**不要**勾 Add README。）

**1. 建立 Render 帳號**

到 [render.com](https://render.com) 用 GitHub 帳號登入。**免費方案不需要信用卡。**

**2. 用 Blueprint 一次建好**

專案根目錄有 `render.yaml`，Render 看得懂：

1. Dashboard 按 **New +** → **Blueprint**
2. 選剛剛推上去的 repo → **Connect**
3. 它會列出要建立的東西：一個 Web Service（`mealvote`）＋一個 PostgreSQL（`mealvote-db`）
4. 按 **Apply**

`render.yaml` 裡已經把資料庫的連線字串接到網站的 `DATABASE_URL` 了，**不用自己複製貼上**。

**3. 等它跑完**

第一次大約 2–4 分鐘。看到 **Live** 就好了，網址長得像 `https://mealvote-xxxx.onrender.com`。

**4. 確認資料庫真的接上了**

打開 `https://你的網址/healthz`，應該看到：

```json
{"ok":true,"storage":"pg","rooms":0}
```

`"storage":"pg"` 才是對的。如果是 `"file"`，代表資料庫沒接上，去 Web Service 的 **Logs** 看警告訊息。

**5. 讓它不要一直睡著**

免費方案閒置 15 分鐘會休眠，下一個人點連結要等大約一分鐘才醒。資料不會掉（在資料庫裡），只是等待很尷尬。

免費的解法：到 [cron-job.org](https://cron-job.org) 註冊，建一個每 10 分鐘打一次 `https://你的網址/healthz` 的排程就好。

（每個月有 750 小時的免費額度，一直醒著大約會用掉 744 小時，剛好在額度內，但只夠一個服務。）

**6. 分享給朋友**

網址直接丟群組。房間連結本身就是入場券，不需要登入。

### ⚠️ 免費 PostgreSQL 三十天會到期

Render 的免費資料庫**建立後 30 天到期**，之後會連不上（還有 14 天寬限期才真的刪掉）。到期時：

1. 建一個新的免費 PostgreSQL
2. 把 Web Service 的 `DATABASE_URL` 換成新的 Internal Database URL
3. Manual Deploy 一次

**不用搬資料** —— 這個 app 的房間本來就是一次性的，程式也會自動清掉 30 天前的房間。到期那天剛好等於全部重來，沒有損失。

到期時服務不會掛掉，它會退回檔案模式繼續跑（log 有警告），只是重啟會掉資料。

### 其他平台

- **Railway**：接 GitHub repo 就會自己認出是 Node 專案。加一個 PostgreSQL 服務，Railway 會自動注入 `DATABASE_URL`。
- **Fly.io**：`fly launch` 之後 `fly volumes create data --size 1`，`fly.toml` 掛到 `/data`，設 `DATA_DIR=/data` 就能用檔案模式持久化（不需要資料庫）。
- **不要用 Vercel / Netlify 的 serverless**：每次請求可能落在不同執行實例，記憶體裡的房間對不起來。這個 app 需要一個「一直在的行程」。

### 環境變數

| 變數 | 預設 | 說明 |
|---|---|---|
| `PORT` | `3000` | 監聽的埠號，多數平台會自動注入 |
| `DATABASE_URL` | 空 | 設了就用 PostgreSQL，沒設就用 JSON 檔 |
| `DATA_DIR` | `./storage` | 檔案模式的存放目錄，指到 volume 掛載點就能持久化 |
| `GOOGLE_MAPS_API_KEY` | 空 | 選填，見下一段 |

## 選填：接上 Google 即時評分

**不設定也完全能用。** 每家餐廳都有「地圖・評分」「看菜單」「查訂位」三個連結，點下去就是 Google Maps 或 Google 搜尋，看得到最新評分、菜單照片和營業時間。這些連結不需要 API key，也不會失效。

如果想讓評分直接顯示在卡片上，設定 `GOOGLE_MAPS_API_KEY` 就會自動啟用，並補上評分、評論數、目前是否營業。

因為呼叫是在**伺服器端**發出的，key 不會出現在瀏覽器裡 —— 這是有後端才有的好處，純前端做不到。查詢結果會快取 24 小時，避免重複消耗額度。

要注意的是，Google Maps Platform 要開通 API key **必須先綁定帳單帳戶（信用卡）**，這是硬性規定。免費額度方面，Google 在 2025 年 3 月把過去的「每月 200 美元抵免」改成分級的免費呼叫次數，Essentials 等級每月 10,000 次；這個 app 的用量遠低於此，實質上不會扣到錢，卡只是拿來驗證身分。

## 讓餐廳變多：從 OpenStreetMap 匯入

內建的精選清單只有 277 筆，而且為了資料正確性，大部分是連鎖品牌（連鎖店的類型、價位、哪些站有分店比較好確定）。實際用起來會覺得推薦來推薦去都是那幾家。

要補上大量的個人小店，跑這一行：

```bash
node tools/import-osm.js
```

它會從 OpenStreetMap 的 Overpass API 撈雙北範圍內所有標記為餐廳的地點，依座標指派最近的捷運站、判斷料理類型，寫進 `data/osm-restaurants.json`。伺服器重啟後就會自動合併進來（畫面上會標「社群資料」以示區別）。

**OpenStreetMap 免費、不需要 API key、不需要綁信用卡**，資料是 ODbL 授權。

幾個實際會遇到的狀況：

- **Overpass 是免費的公共服務，忙碌時會塞住**。腳本內建三個鏡像站與重試，但真的塞爆時就是會失敗，過幾分鐘再跑一次通常就好。
- **OSM 沒有價位資料**，所以匯入的餐廳 `price` 是 null，卡片上不顯示價位。這也是為什麼預算篩選被拿掉了——半數餐廳沒有價位的話，那個篩選只會把它們全部誤殺。
- **資料由志工維護，會有缺漏和過期**。有些店關了還在、有些新店還沒登記。但量遠大於手工清單，而且隨時可以重跑更新。
- **有些店沒有 cuisine 標籤**，腳本會試著從店名猜。台灣街邊小吃在 OSM 上最常沒標籤，所以店名判斷特別鋪滿了小吃關鍵字（肉圓、蚵仔、割包、臭豆腐、米糕、碗粿、麵線、鹹酥雞…）。猜不出來的 restaurant 會被略過，不會亂塞。
- **有幾個標籤在台灣語境下要另外處理**：`rice`（滷肉飯／雞肉飯）、`dumpling`（水餃）、`bento`（便當）在國際慣例上會被歸到台菜／港點／日式，但在台北它們就是小吃，所以特別改掉了。`dim_sum` 則維持港式。
- 手搖飲、超商、藥局、速食連鎖這些會自動排除。

可用參數：

```bash
node tools/import-osm.js --radius=800   # 收離車站 800 公尺內的（預設 500）
node tools/import-osm.js --cafes        # 連咖啡廳也收（預設不收）
```

想先確認程式本身沒問題（不需連網）：

```bash
node tools/osm-lib.test.js
```

## 飯局名稱與時間可以事後改

時間常常會喬。進到房間後按標題旁邊的「✎ 編輯」就能改名稱、日期、時間，存檔後**其他人的畫面會在幾秒內同步更新**。

這個修改只動顯示用的欄位，不影響配對，所以**不會清掉已經產生的推薦與投票**——改個時間不用重投一次。

## 離車站多遠、要走幾分鐘

卡片上會標「出站後約 180 公尺・走路 3 分鐘」。距離是從 OSM 的實際座標到車站算出來的直線距離，步行時間用不動產業界慣用的**每分鐘 80 公尺**換算，不足一分鐘算一分鐘。

因為是直線距離，實際走路會再多一點（要繞路口、找出口）。當成「大概多遠」的參考就好。

精選清單裡的店本身沒有座標，但**如果 OSM 也收錄了同一家店（同名同站），距離會自動繼承過來**——所以跑過 `node tools/import-osm.js` 之後，連鼎泰豐、阜杭豆漿這些手動加的店也會有距離。沒對到的就不顯示，不會亂估。

## 平價小吃是人工整理的

OSM 撈得到店，但**撈不到價位**——而「便宜」正是小吃最重要的資訊。所以 `data/restaurants.js` 裡有一個 `CHEAP_EATS` 區塊，每一筆都標了實際的人均價位。

選店偏向兩種：各站的**夜市與傳統市場**（一定存在、也一定便宜），以及**有名字的老店**。刻意往外圍站別鋪，因為平價小吃本來就不集中在市中心——目前小吃・麵食這一類涵蓋 50 個捷運站。

卡片上 $200 以下標「銅板價」、$350 以下標「平價」，方便一眼掃。

## 加自己的口袋名單

打開 `data/restaurants.js`，往 `CHAINS`（連鎖，一個品牌對多個站）或 `INDIE`（單店）加一筆就好，伺服器重啟生效。

```js
{ name:"你家巷口那間", type:"taiwanese", price:350, station:"公館",
  note:"老闆很兇但滷味很好吃", book:false }
```

`type` 要用 `TYPES` 裡定義的 id（`japanese` `ramen` `sushi` `korean` `hotpot` `bbq` `taiwanese` `sichuan` `canto` `italian` `american` `thai` `izakaya` `brunch` `veggie` `noodle` `buffet`）。`price` 是每人概估消費，純粹顯示用，不確定就填 `null`。地圖與訂位連結會自動生成，不用自己填。

手動加的店會標成「精選」，排序上優先於 OSM 匯入的資料。

## 關於餐廳資料的可信度

這件事必須講清楚：**精選清單是我依既有知識整理的，不是查證過的即時資料。** 開發過程中就抓到幾筆錯的——有已經歇業多年的夜市、有查不到分店的餐廳、也有「某某店隔壁的麵攤」這種根本不算店名的泛稱。這些已經全部移除（共 22 筆）。

剩下的仍可能有錯，因為餐廳開開關關是常態。三個防線：

1. **地圖／菜單／訂位都是搜尋連結**，不是寫死網址，所以不會有連結 404；搜尋關鍵字也刻意放寬成「店名 站名」而不是「店名 捷運X站」，綁太死反而查不到東西。
2. **跑過 OSM 匯入後**，精選清單裡的店如果 OSM 也收錄，會繼承實際座標算出來的距離——有距離的那幾家等於被 OSM 交叉驗證過。
3. **發現有店關了，直接從 `data/restaurants.js` 刪掉那一行就好**，伺服器重啟生效。

如果要一份真正可靠的清單，最實際的做法是跑 OSM 匯入（社群持續維護），再把自己確定還在的店手動加進精選。

## 目前的限制

- **內建的精選清單 323 筆**，其中連鎖品牌仍佔多數（平價小吃那一區是例外，全是獨立店家）。想要更多樣性請務必跑一次 `node tools/import-osm.js`。
- **價位是概估值**，而且 OSM 匯入的餐廳完全沒有價位。所以這個 app **沒有預算篩選**——與其用一個半數資料都缺的欄位去篩，不如不篩。
- **沒有串 API 時，卡片上不會顯示星等數字**，要點「地圖・評分」進 Google 看。這是刻意的 —— 寫死一個評分數字在程式裡，過幾個月就會變成錯的資訊。
- **只支援雙北軌道路網**（台北捷運六線＋兩條新北輕軌，共 139 站）。填「幾站」是很台北的思維，其他縣市要用的話得改成公里數。
- **步行距離是直線距離**，不是實際路徑；而且只有 OSM 收錄的店才有。
- **站數是硬條件**，所以條件填太緊（例如兩個人分別在迴龍和象山、都只肯坐 1 站）就會什麼都配不出來。這是刻意的，畫面上會告訴你是誰卡住了。
- 投票**可以複選**（喜歡的都按下去，再點一次取消），送出後不能反悔，結算時以票數排前三名，同票並列同名次，最多顯示 5 列。但**沒有身分驗證** —— 換個瀏覽器就能再填一個人。朋友之間夠用，不適合拿來辦公投。
- **角色的保密靠的是伺服器不吐資料，不是前端藏起來**。這對朋友聚餐夠了；但拿到房間連結的人都能加入，所以連結本身要當成密碼看待。
- **笨蛋的轉盤只從推薦名單裡抽**，不含神秘店家——不然「不能自己選」的人反而被塞了一家連他自己都不知道是什麼的店。
- **彩蛋那 10 秒是前端計時的**，決定記在瀏覽器的 localStorage。這擋得住「重整一次再想想」，但擋不住刻意去改瀏覽器資料的人。朋友聚餐的小遊戲，做到這裡就夠了；真要防弊得把倒數搬到伺服器上。

## 專案結構

```
server.js               Express API 與路由
data/mrt.js             捷運路網、站名別名、最短路徑
data/restaurants.js     精選餐廳清單（要手動加店改這裡）＋ 合併 OSM 資料
data/osm-restaurants.json  跑過匯入腳本才會出現
lib/recommend.js        推薦演算法：共識區與類型區
lib/roles.js            角色抽籤、隱藏彩蛋、計票規則
lib/roles.test.js       上面那支的離線測試
lib/store.js            持久化：有 DATABASE_URL 走 PostgreSQL，沒有就走 JSON 檔
lib/places.js           選填的 Google Places 串接
tools/import-osm.js     從 OpenStreetMap 匯入餐廳
tools/osm-lib.js        匯入的純邏輯（分類、指派車站、去重）
tools/osm-lib.test.js   上面那支的離線測試
public/                 前端（單頁、無框架、行動裝置優先）
render.yaml             Render 的藍圖：一次建好網站＋免費 PostgreSQL
build-preview.js        產生單檔預覽版 preview.html
e2e.js                  Playwright 端對端測試
```

## 跑測試

```bash
npm install playwright && npx playwright install chromium
npm start                  # 另開一個終端機
node e2e.js
```

會開三個獨立的瀏覽器 context（等於三支不同的手機）模擬開房、填寫、產生推薦、各自看到自己的角色卡、彩蛋的 10 秒視窗（賭一把／放棄／逾時鎖住）、複選投票、依序送出、自動結算、神秘店家揭曉、再玩一局（角色與彩蛋重抽）、改條件與即時同步，並且會**主動檢查隱私邊界**：公開 API 不得帶出 `roles`／`secret`／`ballots`／彩蛋真實店家，結算前任何人畫面上都不得出現票數。

不需連網、不需開伺服器的離線測試：

```bash
node lib/roles.test.js       # 角色與計票規則（權重、下毒、盲選交換的所有組合）
node tools/osm-lib.test.js   # OSM 匯入邏輯（分類、指派車站、去重）
```

## 預覽版

```bash
node build-preview.js
```

會產生 `preview.html`，一個不需要伺服器的單檔版本，可以直接用瀏覽器打開。畫面、餐廳資料與推薦演算法都是引用專案裡的同一份檔案，所以看到的結果跟正式版一致；差別是後端換成瀏覽器內的模擬，多人同步與資料保存看不出來。方便快速調畫面用。
